# Что отсутствует в инструментах платформы MAX

Разбор сделан по исходникам `@maxhub/max-bot-api@0.3.0`, скрипту
`https://st.max.ru/js/max-web-app.js` и открытым issues официальных репозиториев.
Каждый пункт проверен по коду, а не взят из документации.

Цель разбора, понять, что имеет смысл строить самим, а что уже закрыто платформой.
Официальный SDK для бота сделан хорошо: middleware, сессии, сценарии, вебхуки и long polling на месте,
и заменять его не требуется. Пробелы лежат в двух местах: эксплуатация бота под нагрузкой и сторона мини-приложения.

## 1. Транспорт HTTP

| Что проверено | Где | Состояние |
|---|---|---|
| Подмена `fetch` | `dist/core/network/api/client.js` | Вызывается глобальный `fetch`, `ClientOptions` содержит только `baseUrl`. Прокси, тестовый двойник, метрики подключить неоткуда. Открытый issue #287 |
| Таймаут запроса | там же | Не задаётся. `AbortSignal` пробрасывается только если его передал вызывающий код |
| Повторы | там же | Отсутствуют. Единственное исключение: `messages.send` повторяет ошибку `attachment.not.ready` |
| Лимит 30 rps |: | Не соблюдается ничем; документированный лимит платформы остаётся на совести приложения |
| Сборка query | `client.js` | `if (!value) return` отбрасывает `0`, `false` и пустую строку вместе с `undefined` |
| Сборка path | `client.js` | Значения подставляются без экранирования |

Практический эффект: рассылка уведомлений жильцам упирается в 429 и теряет сообщения,
а один зависший запрос к платформе останавливает обработчик навсегда.

**Закрыто в `@maxkit/runtime`:** `createResilientClient`, инъекция `fetch`, таймаут на попытку,
повторы с экспоненциальной задержкой и джиттером, соблюдение `Retry-After`, планировщик под 30 rps,
хуки для метрик. Встраивается без форка: `bot.api = createResilientApi(token)`.

## 2. Обработка апдейтов

Проверено по `dist/bot.js` и `dist/core/network/polling.js`.

1. **Маркер не переживает перезапуск цикла.** Позиция хранится в поле экземпляра `Polling`,
   а `startPolling` при рестарте создаёт новый экземпляр. После сбоя бот продолжает не с той точки, где остановился.
2. **Маркер продвигается до обработки.** В цикле сначала выполняется `this.marker = marker`,
   и только потом `await Promise.all(updates.map(handleUpdate))`. Падение процесса между этими шагами
   означает потерю пачки апдейтов, для заявок в управляющую организацию это «заявка исчезла».
3. **Ошибка обработчика роняет цикл.** Обработчик по умолчанию пробрасывает ошибку дальше;
   отклонённый `Promise.all` попадает в `catch` цикла, где `shouldRetry` для обычной ошибки возвращает `false`.
   Цикл завершается и перезапускается через пять секунд.
4. **Параллелизм не ограничен.** Вся пачка уходит в `Promise.all` разом, бэкпрешера нет.
5. **Порядок внутри чата не гарантирован.** Последовательность соблюдается только внутри `session()`
   через `KeyedExecutor` и только в пределах одного процесса; при нескольких репликах записи в сессию
   затирают друг друга, распределённой блокировки нет.
6. **`process.exitCode = 1`** выставляется в обработчике ошибок по умолчанию: процесс продолжает работать,
   но помечен как аварийный.
7. **Мягкой остановки нет:** `stopPolling()` прерывает цикл, не дожидаясь текущих обработчиков.

**Закрыто в `@maxkit/runtime`:** `UpdateSupervisor`, маркер во внешнем хранилище (`MemoryMarkerStore`,
`FileMarkerStore`) и сохраняется только после обработки всей пачки, гарантия «хотя бы один раз»;
ошибка обработчика остаётся ошибкой одного апдейта; `OrderedScheduler` даёт ограниченный параллелизм
со строгим порядком внутри чата; `stop()` дожидается текущих обработчиков.
Работает поверх публичного API официального SDK: `bot.api` и `bot.middleware()`.

## 3. Хранилище сессий

`MemorySessionStore` создаётся с `timeToLive = Infinity`, а просроченные записи удаляются только при обращении
к тому же ключу. Для бота, где большинство пользователей приходит один раз, это медленный рост памяти.
Реализаций для Redis или базы в пакете нет, только интерфейс `SessionStore`.

## 4. Сторона мини-приложения

| Чего нет | Подробности |
|---|---|
| npm-пакета и типов для Bridge | Только CDN-скрипт `st.max.ru/js/max-web-app.js`, отдающий глобальный `window.WebApp` |
| Серверной проверки подписи `initData` для Node | Алгоритм описан в документации, готовой реализации нет |
| Способа запустить приложение вне клиента MAX | Bridge отвечает только внутри мессенджера; получить токен бота без верифицированного профиля ЮЛ, ИП или самозанятого нельзя |
| Точки входа для событий в WebView | Нативный клиент доставляет события вызовом `window.WebApp.sendEvent(type, json)`: собственная реализация моста обязана её выставить, иначе входящие события теряются на iOS и Android |

Расхождения документации с фактическим поведением Bridge собраны отдельно:
[`max-bridge-protocol.md`](max-bridge-protocol.md), раздел 5.

**Закрыто в `@maxkit/bridge` и `@maxkit/server`:** типизированный клиент с собственным транспортом,
эмулятор клиента MAX, проверка подписи с `timingSafeEqual` и плагин авторизации для Fastify.

## 5. Что чинить не нужно

- Композиция обработчиков, фильтры, сценарии и сессии в официальном SDK сделаны на уровне зрелых
  фреймворков этого класса, своя реализация не даст выигрыша.
- `KeyedExecutor` внутри `session()` корректен и не течёт: очередь ключа удаляется, когда за ней никто не встал.
- Ретрай поллинга на сетевых ошибках в 0.3.0 уже чинён: условие проверяет `TypeError`, который и бросает
  нативный `fetch` (issues #240, #271 закрыты).
