# Проверка подписи `initData`

Мини-приложение получает от клиента MAX строку `WebAppData`. В ней лежат `user.id`, `chat.id`, `start_param`,
всё то, на чём строится авторизация. Клиентская часть подделывается тривиально (это обычный веб-фронтенд),
поэтому **любое решение о доступе принимается только после серверной проверки подписи**.

Реализация: `packages/server/src/init-data.ts`, каноническая сборка строки, `packages/bridge/src/signature.ts`.

## Алгоритм (dev.max.ru/docs/webapps/validation)

1. Взять все параметры `WebAppData`, кроме `hash`. Значения, в URL-декодированном виде.
2. Отсортировать по ключу `a → z`, склеить парами `key=value` через `\n` (0x0A) → `launch_params`.
3. `secret_key = HMAC_SHA256(key: "WebAppData", data: BOT_TOKEN)`.
4. `expected = HEX(HMAC_SHA256(key: secret_key, data: launch_params))`.
5. Сравнить `expected` с параметром `hash`.

## Что проверяет `validateInitData` сверх алгоритма

| Проверка | Зачем |
|---|---|
| `hash` присутствует ровно один раз | `?hash=валидный&hash=любой`: попытка скормить парсеру разные значения |
| `hash`: hex-строка | до `timingSafeEqual`, иначе `Buffer.from` молча съест мусор |
| Сравнение через `timingSafeEqual` | подпись сравнивается за постоянное время, без утечки по таймингу |
| `auth_date` не старше часа | ограничивает окно повторного использования перехваченной строки |
| `auth_date` не из будущего | иначе истёкшую строку можно «омолодить» подменой часов |
| `user.id` присутствует и число | без идентификатора запрос нечего авторизовывать |

Из этого списка эксплуатируемым сценарием подтверждён только разбор до декодирования, он разобран
ниже и воспроизводится. Остальные строки, защита в глубину: рабочего сценария атаки для них
у нас нет, они закрывают классы ошибок, а не известные дыры. Смешивать одно с другим не будем:
проверка, для которой нет сценария, от этого не становится бесполезной, но и уязвимостью
её называть нельзя.

## Почему строку запуска не стоит слать в каждом запросе

Окно доверия к `auth_date`, час, а параметры запуска приходят один раз, при открытии приложения.
Если авторизовать ими каждый запрос, приложение перестанет работать через час, хотя пользователь
никуда не уходил. Расширять окно нельзя: чем оно больше, тем дольше перехваченная строка остаётся
пригодной для повтора.

Поэтому `@maxkit/server` предлагает обмен: приложение один раз отдаёт строку запуска и получает
сессионный токен (`createSessionAuth`), дальше ходит с ним, а строка запуска больше не гуляет по сети.
Срок жизни сессии задаётся отдельно от окна доверия, её можно продлить или отозвать.

## Почему проверка и разбор используют одни и те же пары

Строка запуска разбивается на пары **до** декодирования значений, и данные берутся ровно из тех пар,
по которым посчитана подпись. Иначе получается расхождение, которое выглядит как валидная подпись
при подменённых данных.

В скрипте платформы (`https://st.max.ru/js/max-web-app.js`, метод `parseInitData`, через который
работает геттер `initDataUnsafe`) разбор устроен так:

```js
new URLSearchParams(decodeURIComponent(e)).forEach((e, n) => { … })
```

Строка декодируется целиком, а уже потом делится на пары. Значение `start_param` приходит из диплинка
`https://max.ru/<bot>?startapp=<payload>`, то есть им управляет тот, кто дал ссылку. Если положить
туда закодированные `&` и `=`, после сплошного декодирования они становятся разделителями,
и в разобранных данных появляется лишний параметр:

```
start_param=a%26user%3D{"id":999}   →   start_param=a  и  user={"id":999}
```

Подпись при этом настоящая: платформа подписала строку, в которой `start_param`, одно значение целиком.
Проверено воспроизведением: строка с подписью, посчитанной по правильным парам, проходит проверку,
после чего разбор «сначала декодировать всё» отдаёт `user.id = 999` вместо `1001`.

**Границы утверждения.** Это дефект разбора на клиенте, а не дыра в серверной проверке платформы:
геттер называется `initDataUnsafe` и по договору не предназначен для решений о доступе. Опасен он
тем, что это первая реализация, которую видит разработчик, и перенос её на сервер даёт связку
«подпись верна, пользователь чужой». Наш разбор к этому невосприимчив, и это закреплено тестом.

`parseInitData` разбивает строку на пары и только потом декодирует значения, а `validateInitData`
берёт данные из `params` того же результата `buildDataCheckString`. Проверяется тестами
`packages/bridge/test/init-data-parsing.test.ts` и «значение start_param не подменяет пользователя»
в `packages/server`.

## Как это отлаживается локально

`@maxkit/bridge/mock` умеет подписывать параметры запуска настоящим HMAC:

```ts
const launchParams = await createSignedMockLaunchParams(process.env.BOT_TOKEN, { startParam: 'meter_42' });
```

Локальная разработка проходит ту же серверную проверку, что и продакшен, без ветвлений «если dev, пропустить».
Ошибка в схеме подписи всплывёт на первом же запуске, а не на демо.

## Проверка телефона из `requestContact()`

Отдельная схема: `HMAC_SHA256(key: BOT_TOKEN, data: authDate + phone + userId)`, параметры в алфавитном порядке,
телефон, без ведущего `+`. Реализовано в `verifyContact()`. Официального примера кода нет,
поэтому схему нужно перепроверить на живом токене до финальной сдачи.
