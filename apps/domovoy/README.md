# @domovoy/server

Точка сборки продукта: бот и API в одном процессе, плюс служебные команды.

## Запуск

```bash
createdb domovoy
BOT_TOKEN=<токен> DATABASE_URL=postgresql://localhost:5432/domovoy \
  npm start --workspace @domovoy/server
```

Без `DATABASE_URL` продукт поднимается на хранилище в памяти, данные исчезают
при остановке.

Переменные окружения: `BOT_TOKEN` (обязательна), `DATABASE_URL`, `PORT` (по умолчанию 3000),
`DEFAULT_BUILDING_ID`, `MINI_APP_URL` для кнопки «Открыть приложение», `MAX_API_URL`
для подмены адреса Bot API на эмулятор, `ALLOWED_ORIGINS`, список адресов, откуда
мини-приложению разрешено обращаться к API, через запятую, `MARKER_FILE`, где хранить
позицию в потоке апдейтов (по умолчанию `./state/marker`), и `METRICS_TOKEN`, токен
для чтения `/metrics` (без него страница метрик открыта).

`METER_VISION_URL` включает показания по фотографии табло: адрес службы,
принимающей снимок формой (`file`) и возвращающей `{"value": 126.5}` или
`{"text": "00126,5"}`. При необходимости `METER_VISION_KEY` и `METER_VISION_MODEL`.
Без переменной кнопка со снимком в приложении не появляется, а показания
подаются цифрами, как и раньше.

`HUB_SECRET` включает маршруты для домофонии: `POST /api/hub/alarm` (сработал датчик
протечки или дыма) и `POST /api/hub/guest-entry` (гость вошёл по коду). Секрет приходит
заголовком `x-hub-secret`. Без переменной этих маршрутов нет.

`SPEECH_URL` включает расшифровку голосовых заявок: адрес службы, принимающей запись
формой (`file`) и возвращающей `{"text": "…"}`. Подходит любая совместимая служба, в том
числе поднятая внутри контура. Дополнительно: `SPEECH_KEY`, `SPEECH_MODEL`
и `SPEECH_LANGUAGE` (по умолчанию `ru`). Без `SPEECH_URL` голосовая заявка всё равно
заводится: запись остаётся вложением, а бот просит написать суть одной строкой, и
написанное уходит сообщением по заявке.

`REASONER_URL` включает разбор обращения моделью: по тексту жильца определяются категория,
срочность и короткий заголовок. Ожидается служба, принимающая чат в формате OpenAI,
дополнительно `REASONER_KEY` и `REASONER_MODEL`. Срок модель не назначает: время реакции
и выполнения считает регламент по категории. Срочность, замеченную по ключевым словам
(«прорыв», «дым»), модель понизить не может. Без `REASONER_URL` категорию определяют
ключевые слова.

Если из обращения не понять, что и где случилось, продукт задаёт один уточняющий вопрос
после создания заявки. Ответ уходит сообщением по заявке, молчание ни на что не влияет.
Присоединившемуся к чужой заявке вопрос не задаётся.

`REDIS_URL` необязателен для одного процесса. С ним вне процесса живут три вещи: состояние
диалога бота, сессии мини-приложения и блокировка склейки обращений. Без него после
перезапуска теряется незаконченный диалог, токен одной реплики не работает на другой,
а два одновременных обращения на разные реплики заводят две заявки.

`MINI_APP_URL` это ссылка платформы вида `https://max.ru/<имя_бота>`, а не адрес статики:
код объекта бот дописывает как `?startapp=<код>`, и в параметры запуска его кладёт платформа.

`ALLOWED_ORIGINS` нужен, если приложение и API раздаются с разных адресов: без списка
браузер заблокирует запросы, и приложение покажет пустой экран.

Бот и API работают в одном процессе: уведомления отправляет бот, а статус меняется
и из приложения. При разделении подменяется канал уведомлений в одном месте.

## Демонстрация

```bash
DATABASE_URL=postgresql://localhost:5432/domovoy npm run seed --workspace @domovoy/server
```

Заводит два дома на улице Ленина: шесть квартир в двух подъездах в первом и две во втором.
Жильцов, диспетчера, мастера, управляющего и подрядчика по лифтам, лифты с домофоном
и по три счётчика на квартиру с историей показаний. У Марии и у диспетчера по две квартиры
в разных домах: так проверяется переключение.

Заявки создаются в разных состояниях: в работе с назначенным мастером, новая аварийная
(застряли в лифте), ожидающая ответа жильца, ждущая приёмки, наряд подрядчика по лифту,
три закрытые по одному лифту и одна непринятая жильцом. Обращение соседки присоединяется
к открытой заявке.

Есть история прошлого месяца, включая работу, сданную с опозданием: по ней считается
сравнение периодов в сводке. По второму стояку первого подъезда идут плановые работы:
обращение оттуда получает срок вместо номера заявки, обращение с первого стояка заводит
заявку.

Данные создаются обычными сценариями, а не записываются в базу напрямую.

## Сквозной прогон

```bash
npm run walkthrough --workspace @domovoy/server
```

Играет сценарий целиком и печатает разговор: объявлены плановые работы, жилец переходит
по коду со стояка и получает срок вместо заявки, настаивает, заявка заводится, сосед
сообщает о том же и присоединяется к ней, сотрудники узнают о новой заявке, диспетчер
принимает, мастер отчитывается, жилец возвращает работу с причиной, подаёт показания
счётчиков, голосует на собрании собственников, диспетчер смотрит сводку.

Работает без токена и без сети: вместо платформы локальный эмулятор Bot API, бот и сценарии
настоящие. Прогон закреплён тестом.

## Наклейки

```bash
BOT_NAME=<имя_бота> npm run stickers --workspace @domovoy/server
```

Кладёт в каталог `stickers/` по SVG на каждый объект и общий лист `sheet.html` для печати:
подъезды, стояки, оборудование и отдельно коды квартир. Коды ведут на бота.

Код квартиры печатается в квитанции, а не на двери: он привязывает жильца к помещению.

Уровень коррекции ошибок «M».

Каждый код обратим, тест проверяет, что продукт читает из него тот объект, который был
закодирован.

На листе для печати под подписью стоит сам код: из квитанции его вводят в приложении руками,
а на подъездной наклейке он подсказывает объект, если картинка затёрлась.

## Проверка запуска

Отдельный тест поднимает `dist/main.js` настоящим процессом, с переменными окружения,
HTTP-сервером и приёмом апдейтов, и проверяет, что проверка живости отвечает, а бот в том же
процессе принимает команды. Второй набор поднимает тот же процесс в режиме вебхука: проверяет
подписку у платформы, доставку апдейта на `/bot/updates` и отказ без секрета.
