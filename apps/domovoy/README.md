# @domovoy/server

Точка сборки продукта: бот и API в одном процессе, плюс служебные команды.

## Запуск

```bash
createdb domovoy
BOT_TOKEN=<токен> DATABASE_URL=postgresql://localhost:5432/domovoy \
  npm start --workspace @domovoy/server
```

Без `DATABASE_URL` продукт поднимается на хранилище в памяти, данные исчезают
при остановке. В этом случае он сам заводит набор для показа тем же сценарием, что
и команда `seed`: иначе запуск одной командой открывает пустой дом.

## Переменные окружения

Обязательна одна: `BOT_TOKEN`. Полный список с пояснениями лежит
в [`.env.example`](../../.env.example).

| Переменная | Назначение | Без неё |
| --- | --- | --- |
| `BOT_TOKEN` | токен чат-бота MAX | процесс не стартует |
| `PORT` | порт HTTP-сервера | 3000 |
| `DATABASE_URL` | Postgres, миграции применяются при старте | хранилище в памяти плюс набор для показа |
| `REDIS_URL` | состояние диалога, сессии и блокировка склейки | всё это живёт в памяти процесса, реплика одна |
| `DEFAULT_BUILDING_ID` | дом до привязки квартиры | `dom15` |
| `MINI_APP_URL` | ссылка платформы `https://max.ru/<имя_бота>` | в чате нет кнопки «Открыть приложение» |
| `SITE_URL` | адрес сайта для ссылок на документы продукта | ссылки ведут на `https://domovoy.homes` |
| `MAX_API_URL` | адрес Bot API: подменяется на эмулятор | настоящая платформа |
| `BOT_NAME` | имя бота в ссылках наклеек | `uk_bot` |
| `MARKER_FILE` | позиция в потоке апдейтов | `./state/marker` |
| `SWEEP_FILE` | отметки регулярных проверок, когда нет Redis | `./state/sweep.json` |
| `WEBHOOK_URL`, `WEBHOOK_SECRET`, `WEBHOOK_PATH` | доставка апдейтов вебхуком; путь по умолчанию `/bot/updates` | бот забирает апдейты опросом |
| `ALLOWED_ORIGINS` | откуда мини-приложению разрешено обращаться к API, через запятую | только свой адрес |
| `FRAME_ANCESTORS` | кому разрешено открывать приложение в рамке | `'self' https://max.ru https://*.max.ru` |
| `LANDING_DIR`, `MINIAPP_DIR` | каталоги статики | `landing/dist` и `apps/miniapp/dist`; нет каталога, нет и раздачи |
| `METRICS_TOKEN` | доступ к `/metrics` | страница открыта всем, кто знает адрес |
| `OWNER_MAX_ID`, `OWNER_NAME` | первый управляющий в свежей базе | роли некому раздать |
| `DEMO_ROLES=1` | примерка роли: `/demo` в боте, раздел «Роль» в приложении | роль выдаёт управляющий |
| `HUB`, `HUB_SECRET` | домофония и датчики, маршруты их событий | раздела «Дом» нет, маршрутов событий нет |
| `PAYMENTS` | платёжный шлюз | суммы видны, кнопки оплаты нет |
| `HANDOFF`, `HANDOFF_CHANNEL` | канал передачи обращений смежным организациям и его имя в журнале | передача записывается как ручная |
| `MEETINGS`, `MEETINGS_TITLE` | система заочного собрания и её название для человека | собрание считается, в систему не уходит |
| `CAPITAL_REPAIR`, `CAPITAL_REPAIR_TITLE` | сведения региональной программы и название источника | раздела капремонта нет |
| `GIGACHAT_AUTH_KEY`, `GIGACHAT_SCOPE`, `GIGACHAT_MODEL`, `GIGACHAT_URL` | модель, распознавание речи и чтение табло одним ключом | берётся `REASONER_URL`, а при его отсутствии ключевые слова |
| `REASONER_URL`, `REASONER_KEY`, `REASONER_MODEL` | любая служба с чатом в формате OpenAI | разбор по ключевым словам |
| `SPEECH_URL`, `SPEECH_KEY`, `SPEECH_MODEL`, `SPEECH_LANGUAGE` | отдельная служба расшифровки речи | расшифровывает GigaChat, а без ключа запись остаётся вложением |
| `METER_VISION_URL`, `METER_VISION_KEY`, `METER_VISION_MODEL` | отдельная служба чтения табло | читает GigaChat, а без ключа показание вводится цифрами |
| `NODE_EXTRA_CA_CERTS` | корень доверия для Bot API MAX | запросы к платформе не проходят |

`MINI_APP_URL` это ссылка платформы вида `https://max.ru/<имя_бота>`, а не адрес статики:
код объекта бот дописывает как `?startapp=<код>`, и в параметры запуска его кладёт платформа.

`ALLOWED_ORIGINS` нужен, если приложение и API раздаются с разных адресов: без списка
браузер заблокирует запросы, и приложение покажет пустой экран.

`HUB_SECRET` включает маршруты для домофонии: `POST /api/hub/alarm` (сработал датчик
протечки или дыма) и `POST /api/hub/guest-entry` (гость вошёл по коду). Секрет приходит
заголовком `x-hub-secret`. Без переменной этих маршрутов нет.

`REDIS_URL` необязателен для одного процесса. С ним вне процесса живут три вещи: состояние
диалога бота, сессии мини-приложения и блокировка склейки обращений. Без него после
перезапуска теряется незаконченный диалог, токен одной реплики не работает на другой,
а два одновременных обращения на разные реплики заводят две заявки.

## Модель, речь и снимки табло

Языковую модель точка сборки берёт в таком порядке: сначала GigaChat
(`GIGACHAT_AUTH_KEY`), потом любая служба с чатом в формате OpenAI (`REASONER_URL`).
Без обеих разбор идёт по ключевым словам, и заявка заводится в любом случае.

Порт разбора описывает девять дел, и адаптер закрывает все:

| Метод | Что делает | Без модели |
| --- | --- | --- |
| `understand` | категория, срочность, объект дома, часть дома и заголовок обращения | ключевые слова, заголовок из первого предложения |
| `intent` | вопрос это или сообщение о поломке, и о чём вопрос | вопросительный знак и слова темы |
| `route` | к какому разделу продукта относится написанное | слова раздела |
| `clarify` | уточняющий вопрос об адресе и подписи кнопок к нему | «Где это случилось?» и первые объекты дома |
| `assist` | ответ помощника и раздел, в который он ведёт | подбор раздела по словам |
| `onTopic` | о доме ли вообще спросили | проверка не делается |
| `meaningful` | по делу ли короткий ответ вроде «6» или «не знаю» | доверяем человеку |
| `doing` | какое дело по какой открытой заявке имел в виду человек | номер и слова дела в тексте |
| `digest` | пересказ сводки по дому двумя предложениями | остаются те же числа |

Выбирает модель только из списков, которые ей передали: категории, объекты дома, разделы
роли, номера её собственных заявок. Прав она не добавляет и сроков не назначает, время
реакции и выполнения считает регламент по категории. Срочность, замеченную по ключевым
словам («прорыв», «дым»), модель понизить не может.

Ответы службы держатся в памяти 30 секунд, до 32 записей: разбор одного сообщения
повторяет одни и те же запросы. Неудачный ответ не запоминается. Помощнику на ответ даётся
20 секунд, остальным делам 8.

Голосовое сообщение и снимок табло счётчика разбирает тот же GigaChat тем же ключом:
файл уходит в его хранилище (`POST /files`), прикладывается к вопросу и после ответа
удаляется оттуда. Предел: 15 МБ на изображение, 35 МБ на запись, 30 секунд на разбор.

Отдельные службы остаются и нужны, только если их задали: `SPEECH_URL` принимает запись
формой (`file`) и отвечает `{"text": "…"}`, `METER_VISION_URL` принимает снимок и отвечает
`{"value": 126.5}` или `{"text": "00126,5"}`. Заданная служба идёт первой, GigaChat
подставляется, когда её нет.

Без того и другого голосовая заявка всё равно заводится: запись остаётся вложением, а бот
просит написать суть одной строкой. Показание тогда подаётся цифрами, а кнопка со снимком
табло в приложении не появляется.

Распознанное с фотографии число само в начисление не уходит: продукт показывает, что
увидел, и ждёт нажатия.

Если из обращения не понять, что и где случилось, продукт задаёт один уточняющий вопрос
после создания заявки. Ответ уходит сообщением по заявке, молчание ни на что не влияет.
Присоединившемуся к чужой заявке вопрос не задаётся.

Если из обращения не понять, что и где случилось, продукт задаёт один уточняющий вопрос
после создания заявки. Ответ уходит сообщением по заявке, молчание ни на что не влияет.
Присоединившемуся к чужой заявке вопрос не задаётся.

Бот и API работают в одном процессе: уведомления отправляет бот, а статус меняется
и из приложения. При разделении подменяется канал уведомлений в одном месте.

## Команды консоли

Собранный CLI лежит в `apps/domovoy/dist/cli.js`. Без аргументов он печатает этот же
список. Базу он берёт из `DATABASE_URL`, имя бота для наклеек из `BOT_NAME`.

| Команда | Что делает |
| --- | --- |
| `seed` | очистить хранилище и наполнить демонстрационными данными |
| `stickers [--style <имя>]` | наклейки с кодами объектов в каталог `stickers/` |
| `make-manager <maxUserId> [имя]` | назначить первого управляющего |
| `building --code --address --company --zone --emergency --phone --email --hours --office --office-hours` | карточка дома |
| `add-building --code --address --company --owner --zone --manager [--manager-name]` | завести дом, в том числе другой организации |
| `import-apartments <файл.csv>` | завести дом списком квартир с приборами |
| `import-equipment <файл.csv>` | оборудование дома: код, название, вид |
| `export-readings` | показания за прошлый месяц в CSV для ГИС ЖКХ |
| `export-requests` | реестр заявок за прошлый месяц в CSV |
| `walkthrough` | проиграть сценарий целиком: бот, сценарии и эмулятор платформы |

`seed`, `stickers` и `walkthrough` доступны ещё и как `npm run <имя> --workspace @domovoy/server`.
Примеры вызовов с переменными окружения собраны в README корня, раздел «Запуск без Docker».

## Демонстрация

```bash
DATABASE_URL=postgresql://localhost:5432/domovoy npm run seed --workspace @domovoy/server
```

Заводит два дома на улице Ленина: шесть квартир в двух подъездах в первом и две во втором.
Жильцов, диспетчера, мастера, управляющего и подрядчика по лифтам, лифты с домофоном
и по три счётчика на квартиру с историей показаний. У Марии и у диспетчера по две квартиры
в разных домах: так проверяется переключение.

Заявки создаются в разных состояниях: в работе с назначенным мастером, новая аварийная
(застряли в лифте), ожидающая ответа жильца, ждущая приёмки, наряд подрядчика по лифту,
три закрытые по одному лифту и одна непринятая жильцом. Обращение соседки присоединяется
к открытой заявке.

Есть история прошлого месяца, включая работу, сданную с опозданием: по ней считается
сравнение периодов в сводке. По второму стояку первого подъезда идут плановые работы:
обращение оттуда получает срок вместо номера заявки, обращение с первого стояка заводит
заявку.

Данные создаются обычными сценариями, а не записываются в базу напрямую.

## Сквозной прогон

```bash
npm run walkthrough --workspace @domovoy/server
```

Играет сценарий целиком и печатает разговор: объявлены плановые работы, жилец переходит
по коду со стояка и получает срок вместо заявки, настаивает, заявка заводится, сосед
сообщает о том же и присоединяется к ней, сотрудники узнают о новой заявке, диспетчер
принимает, мастер отчитывается, жилец возвращает работу с причиной, подаёт показания
счётчиков, голосует на собрании собственников, диспетчер смотрит сводку.

Работает без токена и без сети: вместо платформы локальный эмулятор Bot API, бот и сценарии
настоящие. Прогон закреплён тестом.

## Наклейки

```bash
BOT_NAME=<имя_бота> npm run stickers --workspace @domovoy/server
```

Кладёт в каталог `stickers/` по SVG на каждый объект и общий лист `sheet.html` для печати:
подъезды, стояки, оборудование и отдельно коды квартир. Коды ведут на бота.

Код квартиры печатается в квитанции, а не на двери: он привязывает жильца к помещению.

Уровень коррекции ошибок «M».

Каждый код обратим, тест проверяет, что продукт читает из него тот объект, который был
закодирован.

На листе для печати под подписью стоит сам код: из квитанции его вводят в приложении руками,
а на подъездной наклейке он подсказывает объект, если картинка затёрлась.

## Проверка запуска

Отдельный тест поднимает `dist/main.js` настоящим процессом, с переменными окружения,
HTTP-сервером и приёмом апдейтов, и проверяет, что проверка живости отвечает, а бот в том же
процессе принимает команды. Второй набор поднимает тот же процесс в режиме вебхука: проверяет
подписку у платформы, доставку апдейта на `/bot/updates` и отказ без секрета.
