# @maxkit/sessions

Состояние диалога вне процесса: хранилище сессий поверх Redis, распределённая блокировка
и посредник, который связывает их с ботом.

## Зачем

Сессии официального SDK живут в памяти процесса. Пока экземпляр один, этого достаточно;
дальше начинаются две беды:

- **Перезапуск.** Жилец, начавший оформлять заявку, отправляет описание в пустоту:
  бот забыл, что ждал его.
- **Несколько реплик.** Два сообщения одного человека попадают на разные экземпляры,
  оба читают состояние, оба его перезаписывают, одно изменение теряется.

## Как подключается

```ts
import { DistributedLock, KeyValueSessionStore, distributedSession, fromNodeRedis } from '@maxkit/sessions';

const kv = fromNodeRedis(redisClient);

bot.use(
  distributedSession({
    store: new KeyValueSessionStore<DialogState>(kv),
    lock: new DistributedLock(kv),
  }),
);
```

Посредник берёт блокировку по ключу сессии, читает состояние, отдаёт его обработчику
и записывает обратно. Пока идёт обработка, второй апдейт того же человека ждёт,
и получает уже изменённое состояние, а не то, что было до него.

Ключ сессии по умолчанию `<user_id>:<chat_id>`, как в официальном SDK, поэтому подмена
хранилища не меняет поведение.

Если блокировку не удалось получить за отведённое время, поведение выбирается настройкой:
`throw`, отдать ошибку наверх, `skip`, обработать апдейт без сессии. Второе годится
для команд, которым состояние не нужно, и не годится для диалогов.

## Блокировка

`DistributedLock` устроена вокруг двух свойств, без которых блокировка вредна:

- **Владение подтверждается токеном.** Снять или продлить блокировку может только тот,
  кто её взял, даже если срок успел истечь и ключ достался другому.
- **Проверка владения и действие, одна операция.** Снятие и продление выполняются
  скриптом на стороне Redis: между «прочитали значение» и «изменили ключ» блокировка
  может истечь, и неатомарная проверка вернула бы её прежнему владельцу, то есть
  впустила бы в критическую секцию двоих.

Пока задача выполняется под `withLock`, блокировка продлевается сама: срок её жизни
задаётся из расчёта «переживём смерть процесса», а не «успеем доделать работу».

## Клиенты Redis

`ioredis` принимает флаги позиционно, `node-redis`, объектом, поэтому пакет работает
с узким интерфейсом `KeyValueClient`, а конкретные клиенты подключаются адаптерами
`fromIoredis` и `fromNodeRedis`. Для тестов и однопроцессного запуска есть
`MemoryKeyValueClient` с теми же гарантиями и управляемыми часами.
