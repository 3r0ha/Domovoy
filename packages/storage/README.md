# @domovoy/storage

Хранилище продукта поверх Postgres. Реализует тот же интерфейс `Repository`, что и хранилище
в памяти, поэтому сценарии, бот и API при переходе на базу не меняются, меняется только
сборка приложения.

## Запуск

```bash
createdb domovoy
DATABASE_URL=postgresql://localhost:5432/domovoy npm start --workspace @domovoy/server
```

Миграции применяются при старте: применённые записываются в таблицу `schema_migration`,
поэтому повторный запуск ничего не ломает и разворачивание базы сводится к одной команде.

## Почему SQL, а не Prisma

Схема была описана для Prisma, но `prisma generate` не может скачать свои движки в этом
окружении: соединение обрывается на каждой попытке, а без сгенерированного клиента Prisma
не работает.

Источник правды один: миграция [`migrations/001_init.sql`](migrations/001_init.sql). При
появлении доступа к движкам Prisma поднимет ту же схему через `prisma db pull`.

Тесты идут по настоящей базе и проверяют то, что не проверяется на двойниках: восстановление
объекта заявки из колонок, рост истории переходов, порядковые номера в пределах дома,
уникальность номера и сроки плановых работ на уровне ограничений базы.

## Устройство схемы

Заявка хранит объект разложенным по колонкам (`target_kind`, `apartment_id`, `entrance`,
`riser`, `equipment_code`), а не одним JSON: по ним строятся индексы.

История переходов лежит в отдельной таблице, которая только дописывается. Хранилище добавляет
недостающие события, сравнивая количество сохранённых с тем, что пришло из домена.

Снимки привязаны к событию, а не к заявке. Файлы из мини-приложения лежат в базе байтами
(`attachment_file`), из чата вложения приходят ссылкой на файл платформы.

Адресаты объявления сохраняются списком квартир: по нему считается охват и отмечается
прочтение.

Плановые работы хранятся колонками того же объявления. Ограничение таблицы требует, чтобы
вид работ и обе границы срока заполнялись вместе.

У дома есть владелец (`building.company_id`): по нему сотрудник видит только дома своей
организации. У жильца квартир бывает несколько (`resident.apartment_ids`), поэтому люди дома
выбираются и по текущей квартире, и по списку, а на массив стоит gin-индекс.

Миграции лежат файлами `NNN_имя.sql` и применяются по порядку. Каждая идёт своей транзакцией
под advisory-блокировкой, поэтому две реплики, стартовавшие одновременно, применяют её один раз.

## Нумерация заявок

Порядковый номер заявки считается по уже созданным заявкам того же месяца. При одновременном
создании двух заявок номера могут совпасть, от этого защищает ограничение уникальности
в базе, и вызывающий код повторяет попытку.

## Тесты

```bash
createdb domovoy_test
npm test --workspace @domovoy/storage
```

Адрес базы берётся из `DATABASE_URL`, по умолчанию, локальная `domovoy_test`. Если базы нет,
набор пропускается, а не падает: на чужой машине Postgres может не оказаться.
