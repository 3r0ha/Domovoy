# @maxkit/server

Серверная часть мини-приложения MAX: проверка подписи параметров запуска, обмен их на сессию
и авторизация маршрутов Fastify.

## Проверка подписи

```ts
import { validateInitData } from '@maxkit/server';

const { userId, data } = validateInitData(initData, { botToken: process.env.BOT_TOKEN });
```

Сверх алгоритма платформы проверяется то, что обычно и ломает такие реализации: параметр `hash`
должен встречаться ровно один раз и быть hex-строкой, подписи сравниваются за постоянное время,
`auth_date` не может быть из будущего и не старше окна доверия, а данные берутся ровно из тех пар,
по которым посчитана подпись. Подробности и разбор атаки через `start_param`:
[`docs/init-data-validation.md`](../../docs/init-data-validation.md).

## Авторизация маршрутов

```ts
import { maxAuth } from '@maxkit/server';

app.get('/health', handler);                        // публичный

await app.register(async (scope) => {
  await scope.register(maxAuth, { botToken });
  scope.get('/requests', async (req) => list(req.max.userId));   // защищённый
});
```

Fastify инкапсулирует плагины, поэтому проверка навешивается только на маршруты своей области
видимости. Публичная и приватная части API разделяются структурой приложения, а не проверками
внутри обработчиков.

## Сессия вместо параметров запуска

Параметры запуска приходят один раз, при открытии приложения, и живут ограниченное время.
Если слать их в каждом запросе, приложение перестаёт работать, как только истечёт окно доверия
к `auth_date`, при этом пользователь никуда не уходил и экран не закрывал.

Приложение обменивает строку запуска на сессионный токен сразу после старта и дальше ходит с ним:

```ts
import { createSessionAuth, maxSession } from '@maxkit/server';

const auth = createSessionAuth({ botToken, sessionTtlMs: 12 * 60 * 60 * 1000 });

app.post('/auth/session', async (request) => auth.issue(request.headers['x-max-init-data']));

await app.register(async (scope) => {
  await scope.register(maxSession, { auth });
  scope.get('/requests', async (request) => list(request.max.userId));
});
```

`request.max` в обоих режимах имеет одну форму, поэтому обработчики не знают, как именно вошёл
пользователь. `auth.refresh(token)` продлевает сессию новым токеном и гасит прежний,
`auth.revoke(token)` прекращает её немедленно.

Хранилище сессий подключается через интерфейс `SessionTokenStore`. В комплекте два: в памяти
процесса, этого достаточно одному экземпляру, и `KeyValueSessionTokenStore` поверх любого
хранилища ключ-значение с формой `get`/`set`/`delete`, например обёртки над Redis
из [`@maxkit/sessions`](../sessions):

```ts
const auth = createSessionAuth({ botToken, store: new KeyValueSessionTokenStore(kv) });
```

Без общего хранилища токен, выданный одной репликой, не работает на другой: приложение
получает «сессия не найдена» и входит заново через раз. Запись живёт в хранилище чуть дольше
собственного срока, тогда истёкшая сессия отличается от неизвестного токена.

## Телефон из requestContact

`verifyContact()` сверяет подпись телефона, полученного через `WebApp.requestContact()`.
Официального примера кода для этой схемы нет, поэтому её нужно перепроверить на живом токене
до сдачи решения.

## Тесты

```bash
npm test --workspace @maxkit/server
```

38 тестов: подпись и её подделка, окно свежести, дублирующийся `hash`, попытка подмены пользователя
через `start_param`, область видимости плагина, выдача и проверка сессии, истечение, обновление и отзыв,
а также сессии в общем хранилище: токен одной реплики работает на другой, испорченная запись читается
как отсутствие сессии.
