# @maxkit/runtime

Рантайм для ботов MAX: устойчивый транспорт и надёжная обработка апдейтов поверх официального SDK.

Пакет ничего не заменяет и не форкает. `@maxhub/max-bot-api` остаётся источником типов, композиции
обработчиков, сценариев и сессий, здесь закрывается только то, что относится к эксплуатации бота
под нагрузкой и к сбоям. Подробный разбор, зачем это нужно: [`docs/sdk-gap-analysis.md`](../../docs/sdk-gap-analysis.md).

## Транспорт

```ts
import { Bot } from '@maxhub/max-bot-api';
import { installResilientApi } from '@maxkit/runtime';

const bot = new Bot(process.env.BOT_TOKEN);
installResilientApi(bot, process.env.BOT_TOKEN, {
  timeoutMs: 30_000,
  rateLimit: { rps: 30 },
  retry: { attempts: 3 },
  hooks: {
    onRetry: ({ apiMethod, status, delayMs }) => log.warn({ apiMethod, status, delayMs }, 'повтор запроса'),
    onRateLimitWait: ({ waitedMs }) => metrics.rateLimitWait.observe(waitedMs),
  },
});
```

Что добавляется:

- **Таймаут на попытку**, зависший запрос к платформе не блокирует обработчик навсегда.
- **Повторы по политике, учитывающей идемпотентность.** `429` и ошибки шлюза (`502`, `503`, `504`)
  повторяются для любого метода: запрос не был обработан. `500` и обрывы сети повторяются только для
  `GET`, `PUT` и `DELETE`, слепой повтор `POST /messages` означает второе сообщение жильцу,
  а ключа идемпотентности у Bot API нет.
- **Соблюдение лимита 30 rps** с равномерным темпом и очередью FIFO. Заголовок `Retry-After` от платформы
  тормозит все запросы, а не только отвергнутый.
- **Своя реализация `fetch`**, прокси, mTLS, тестовый двойник.
- **Хуки** `onRequest`, `onResponse`, `onRetry`, `onFailure`, `onRateLimitWait` для метрик и логов.

## Обработка апдейтов

```ts
import { createBotSupervisor, FileMarkerStore } from '@maxkit/runtime';

const supervisor = createBotSupervisor(bot, {
  markerStore: new FileMarkerStore('./state/marker'),
  concurrency: 16,
  onHandlerError: (error, update) => log.error({ error, update }, 'обработчик апдейта упал'),
});

process.on('SIGTERM', () => void supervisor.stop());
await supervisor.start();
```

Гарантии:

1. **Ничего не теряется.** Маркер сохраняется во внешнем хранилище и только после того, как вся пачка
   обработана. Это «хотя бы один раз»: после падения возможен повтор, поэтому обработчики должны быть
   идемпотентны, заявка создаётся по ключу, а не вслепую.
2. **Позиция переживает перезапуск.** После рестарта бот продолжает с того места, где остановился.
3. **Ошибка обработчика не роняет цикл.** Один «ядовитый» апдейт уходит в `onHandlerError`
   и не блокирует остальные.
4. **Порядок внутри чата.** Два сообщения одного пользователя обрабатываются последовательно,
   разные чаты, параллельно, общее число одновременных обработчиков ограничено.
5. **Мягкая остановка.** `stop()` перестаёт забирать апдейты и дожидается текущих обработчиков:
   заявка либо записана целиком, либо не бралась в работу.
6. **Недоступное хранилище позиции не заставляет бота молчать.** Если позицию не прочитать,
   бот стартует с текущего момента; если не записать, цикл продолжается, а о неудаче
   сообщается в `onMarkerError` и считается в `stats.markerErrors`. Цена, повтор пачки
   после перезапуска, и это дешевле молчащего бота.

Супервизор использует только публичные точки бота, `bot.api` и `bot.middleware()`.

## Приём вебхука

В режиме вебхука платформа доставляет апдейты параллельными HTTP-запросами, поэтому два сообщения
одного пользователя обрабатываются одновременно. `WebhookReceiver` выстраивает их в ту же очередь,
что и супервизор при опросе.

```ts
import { WebhookReceiver } from '@maxkit/runtime';

const receiver = new WebhookReceiver({
  secret: process.env.WEBHOOK_SECRET,
  handleUpdate: (update) => processUpdate(update),
  concurrency: 16,
});

http.createServer(receiver.callback()).listen(3000);
process.on('SIGTERM', () => void receiver.drain());
```

- Секрет обязателен и сверяется за постоянное время до чтения тела: адрес вебхука попадает
  в логи прокси, и тело запроса от постороннего читать не нужно.
- Тело запроса ограничено по размеру и обрывается на превышении, а не копится в памяти.
- Обрыв соединения на середине запроса обрабатывается: необработанное событие `error`
  на потоке завершило бы процесс целиком.
- Повторная доставка одного апдейта не приводит к повторной обработке.
- Ответ платформе отдаётся сразу, обработчик выполняется отдельно; `drain()` дожидается его при остановке.

## Отдельные части

`RateLimiter`, `OrderedScheduler`, `Semaphore`, `MarkerStore` экспортируются отдельно: их можно
использовать вне бота, например для собственных фоновых задач. Часы и ожидание внедряются через
параметры, поэтому поведение проверяется тестами без реального времени.

npm test --workspace @maxkit/runtime

порядок и параллелизм планировщика, сохранение маркера, переживание сбоев, мягкая остановка,
проверка секрета вебхука, предел размера тела и отсев повторной доставки.
